# 长任务接续与逐项检查

2026-10-30。在第一版「意见 → 待办 → 执行回报 → 复查 → 验收」基础上，补齐中途进展、上下文恢复与返工信息传递。仍在开发分支，未发布新标签。

后续顾问与执行 Agent 直接交流、评分与可视化记录见 [协作验证](dialogue-review.md)。本文保留接续功能的验证快照。

## 解决的实际断点

1. 原来只有最终回报，长任务中途的进展与下一步没有单独保存。现在主力可用 `in_progress` 保存有意义的检查点，必须写明下一步，任务显示「主力处理中」，不会增加待验收或已验证数量。
2. 原来重新开放只改变状态，下次交付没有上次报告或人工修改理由。现在预览与交付包含最近人工决定、上次派单的进展、证据摘录和下一步；旧报告有历史标记，不冒充新一轮成果。
3. 原来模型只能写回报，无法读取插件工作台恢复上下文。新增只读 `advisor_work_context`，以宿主实际执行会话为边界，读取任务队列或某项任务的范围、验收条件、有效派单 ID、最近报告和人工决定。
4. 原来检查证据是一整段文字，失败和未执行项容易被忽略。现在可附最多 12 个检查项，每项包含名称、报告状态和证据或未执行原因。界面、复查摘录和导出都保留这些信息。
5. 工作台增加「待交付 / 执行中 / 需解阻」筛选，列表显示状态对应的下一步提示，搜索覆盖验收条件、最近报告和下一步。已结束派单的下一步不冒充当前队列指令。
6. 增加「资料研究」和「文档交付」提问模板：支持来源核查、事实与推断区分、内容缺口和交付清单，不自动调用模型或扩大材料权限。

## 日常使用

- **任务进行一半**：主力在有意义的节点回报进展、检查证据和下一步。工作台显示回报时间及完整报告历史，不生成虚假百分比，不把进度回报称为完成。
- **会话中断后继续**：可以告诉主力「读取当前会话顾问待办，接着已交付任务的最后一个检查点继续」。工具返回的报告只是保存的信息，主力仍需核对实际文件与环境。没有会话 ID、请求另一会话的任务、无效分页参数都会被拒绝。
- **需要补资料或返工**：查看下一步和阻塞原因。当前任务仍在处理时重新开放，需要确认已经检查主对话，避免与执行中的工作重复。编辑范围后重新预览，再交付；新派单 ID 会使旧回报失效。
- **准备验收**：逐项查看「报告通过 / 报告失败 / 尚未执行」。后两种情况有醒目提示，用户可以补查、复查或附理由作人工决定。模型报告通过不是独立验证，也不代表覆盖了全部验收条件。

## 工具示例

列表查询默认最多返回 20 项未关闭任务，不包含完整报告、原意见或派单令牌；使用 `nextOffset` 继续读取。指定任务 ID 才返回该任务的详细信息（可查看已关闭任务）。没有跨会话搜索，也没有隐式派单。

```json
{"workItemId":"从当前会话列表取得的任务 ID"}
```

以上作为 `advisor_work_context` 参数。主力写检查点时调用 `advisor_work_report`，示例字段如下；ID 必须来自真实已交付任务：

```json
{
  "workItemId": "真实任务 ID",
  "assignmentId": "当前有效派单 ID",
  "outcome": "in_progress",
  "summary": "已完成正文结构核对，来源核查尚未结束。",
  "evidence": "已核对提供的两段原文；第三项只有二手摘要。",
  "nextStep": "取得第三项原文，核对结论是否被摘要扩大。",
  "checks": [
    {"label":"原文支持结论", "status":"not_run", "evidence":"第三项原文尚未提供。"}
  ]
}
```

进度或结果缺少必要字段时整条拒绝，不落半份记录。同一个工具调用 ID 重放不重复添加。旧客户端没有检查项或下一步的最终报告仍可读，`working` 是新增状态，升级时应一并更新服务端与客户端。

每项保留最近 20 份报告（含检查点）；建议在阶段完成、遇阻或交接时报告，避免逐步刷屏。原有每项 80 条事件和每会话 500 项上限不变。队列和指定任务读取都不发模型请求；真正继续执行仍会产生宿主正常模型/工具开销。新工具不会自动恢复会话、唤醒模型或启动定时工作。
